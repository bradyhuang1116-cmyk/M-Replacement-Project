# 当前实现状态说明（2026-06-10）

> 本文档说明 local-test 分支的当前实现逻辑、与早期版本的区别、以及交付/对接待办。

## 一、这一轮做了什么（与之前的区别）

早期版本：vLLM 跑在百度官方 Docker 镜像里（运行时挂载本地模型），核心算法是明文 .py，
通过文件夹监听（watch_folder）接任务。本轮围绕**源码/模型保护**和**正确的 PLM 对接方式**做了重构。

### 1. 模型已封装进自打镜像（不再挂载）
- **之前**：`docker run 百度镜像 -v 本地models挂载`，宿主机能看到模型目录。
- **现在**：自打镜像 `nodexelocr:v1`，模型 COPY 进镜像内部（中性目录名 nodexel-ocr），
  零挂载启动 `docker run -d --gpus all -p 8080:8080 nodexelocr:v1`。
  Dockerfile 见 `docker/Dockerfile.nodexel` + `docker/entrypoint.sh`（降日志级别隐藏模型路径）。
- **镜像不进 git**（22GB），通过云盘/移动硬盘交付。导出命令：
  `docker save nodexelocr:v1 | gzip > NodexelOCR.tar.gz`

### 2. 核心代码已 Nuitka 编译为 .pyd（源码保护）
- `modules/` 全部 13 个模块 + `config.py` 编译成机器码 `.pyd`，客户拿不到可读源码。
- 编译脚本：`scripts/compile_core.sh`（首次需 gh-proxy 加速下载 MinGW，见 memory）。
- 保留 .py 的只有：`api/`（接口转发层，无算法）、`start_v2.py`（入口）、`__init__.py`。
- **本仓库(local-test)存的是 .py 源码**；编译后的 .pyd 交付物在另一分支（见三）。

### 3. manual_editor 打包成 exe
- 审核员工具用 PyInstaller 打包成单文件 `ManualEditor.exe`（含 Python+PySide6+字体），
  双击即用。spec：`build_tools/manual_editor.spec`。
- 保存逻辑改为**直接覆盖原图**（同目录、原名，不再建 edited/ 子目录）。

### 4. 图纸处理日志表（O/N）
- `modules/process_log.py`：SQLite 表 `process_log`，字段对齐客户 R_V_TD_FILEPATH。
- **O/N 定义**：O = 用了 OCR（method='ocr'，扫描件），N = 未用 OCR（method='vector'，矢量PDF）。
- worker 路径和 api 面板路径**都会写**日志。
- 测试期额外输出 CSV `data/process_log.csv`（开关 `_WRITE_CSV_LOG`，交付前设 False）。
- PLM 来源字段（docnumber/work_seq）单机拿不到，留空，待对接补。

### 5. 输出文件命名
- **之前**：`H + 原名 + -R.tif`（加前缀后缀）。
- **现在**：保持原名；仅当输出目录==输入目录时加 `_replaced` 避免覆盖输入。

### 6. PLM 对接方式改为 Oracle 直连（推翻文件夹监听）
- **之前**：watch_folder 监听文件夹接任务。
- **现在**：生产走 Oracle 双表直连（对方实现）。watch_folder **保留作本地测试入口**，
  生产不启动。详见二。

## 二、关键约束与坑（接手必读）
- **CUDA 版本**：paddlepaddle-gpu 必须装 **CUDA 12.9 构建版**（cu129 源），本机 RTX 5070 Ti
  (Blackwell) 用 cu126 会导致 OCR 静默返回空（不报错但识别全失败）。见 requirements_local.txt 注释。
- **两个模型**：VLM(PaddleOCR-VL) 在镜像内跑；红框检测 PaddleOCR v5 在**宿主机**本地跑（需宿主机装 paddle）。
- 部署：客户内网无公网，全离线交付。打包脚本 `scripts/离线打包.sh`（尚未实跑生成交付包）。
- Windows 服务：`scripts/install_service.bat`（nssm 注册开机自启）。

## 三、PLM-Oracle 对接待办（对方实现，我方提供接口）

> 生产对接 = 直连客户 Oracle 双表，**由对方/客户团队实现**。我方提供处理接口
> `process_single_file(file_path, output_dir)`，对方调用并据返回回写数据库。

### 对接流程（来自客户文档《光栅图处理软件与PLM系统的交互机制》）
1. **读本机 IP 决定连哪个库**（读外部配置 server.properties）：
   - `10.237.126.127` → database dbg13, schema meseplm（开发）
   - `10.237.126.77`  → database rtn13, schema meseplm（生产）
2. **轮询任务表**取待处理：
   ```sql
   SELECT DOCNUMBER, TH, BBH, FILENAME, WORK_SEQ
   FROM R_V_TD_FILEPATH WHERE ISPROCESS='0' ORDER BY UPD_TIMESTAMP ASC
   ```
3. **查原图表定位物理路径**：
   ```sql
   SELECT LOCATION FROM SIPM197
   WHERE DEL=0 AND WKAID<>'3' AND TH=? AND BBH=? AND FNAME=? AND DOCNUMBER=? AND WORK_SEQ=?
   ```
4. **拼绝对路径**：IP=.127 → `D:\PLM719\filedata` + LOCATION；IP=.77 → `D:\PLM\filedata` + LOCATION
5. **调我方接口处理**：
   ```python
   result = process_single_file(图纸绝对路径, 输出目录)
   # result["method"]: "vector"(矢量) 或 "ocr"(扫描件)
   # result["total"]: 替换数；result["status"]: success/...
   ```
6. **归档**：保存到 `D:\SMEC\<WORK_SEQ>\<TH>-<BBH>\<FILENAME>`（先递归建目录）
7. **事务回写双表**（任一失败回滚）：
   ```sql
   UPDATE SIPM197 SET OCR=?, PTIME=SYSDATE WHERE ...
   UPDATE R_V_TD_FILEPATH SET ISPROCESS='1', OCR=?, UPD_USER='LMT', UPD_TIMESTAMP=SYSDATE
     WHERE ... AND ISPROCESS='0'
   ```
   - **OCR 字段值**：`O if result["method"]=="ocr" else "N"`（O=用OCR，N=未用OCR）

### 我方已提供的对接支撑
- `process_single_file()` 接口（返回 method/total/status/output_path）
- `modules/process_log.py` 已按 R_V_TD_FILEPATH 字段记录 O/N（对方可参考或直接读）
- `oracledb` 已在 requirements（thin 模式，无需 Instant Client）

### 对方实现要点建议
- Oracle 驱动用 `oracledb` thin 模式
- 双表更新放一个事务，任一失败 rollback
- 防重复消费：`SELECT ... FOR UPDATE SKIP LOCKED` 或单实例串行
- 路径不存在/定位失败 → 记日志告警，不静默跳过
